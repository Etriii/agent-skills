# Ultimate QA

Start a new project with `$ultimate-qa run` or `$ultimate-qa initialize`. If no state exists, guide the user to initialize before a standalone `audit` or `plan`. Resolve the kit location from `ULTIMATE_QA_KIT`, an adjacent `qa-template/` directory, or `kit-location.txt` in this skill folder. If none works, ask for the kit path. Read the kit's `README.md`, `01_QA_AGENT_PROMPT.md`, `02_QA_CHECKLIST.md`, and relevant guides; the skill commands below control when work stops.

In Codex, invoke `$ultimate-qa run`; in Claude Code, invoke `/ultimate-qa run`. Both accept the same subcommands and optional `--client` argument. These are agent chat instructions, not terminal commands.

Use the application opened in the agent session as the target. Resolve it with `git -C <session-directory> rev-parse --show-toplevel`, confirm it is the intended application, and use that same absolute root for every helper and output path. Quote paths containing spaces. Keep `qa-findings/` inside that root and reject symlinks or junctions redirecting QA output. If the session is in the kit or a parent folder with multiple applications, ask which application to review. A user-wide skill installation changes availability, not the review target. Never use the skill's installation directory as the project root.

## Commands

- `run [--client]`: Perform the combined workflow below, continuing between stages without another command from the user. `--client` authorizes client preparation after the plan; it never authorizes implementation, approval decisions, deployment, sending documents, or destructive testing.
- `initialize`: Identify the application root, inspect existing plans, requirements, progress, Git, Docker, Compose, databases, available test accounts, and existing QA output. Ask the kit's five intake questions together, especially where an existing plan lives. Run the preflight in `tools/qa_preflight.py` before trying runtime checks. After intake, run `python <kit>/skills/ultimate-qa/scripts/qa_state.py init --project <root>`. The helper creates `qa-findings/`, the first version state, and a verified Git ignore entry. Copy the kit's requirement templates if absent; prefill only facts supported by the project. Record preflight and intake decisions. Do not overwrite an existing review; reconcile it first.
- `audit [scope]`: Read requirements and the selected checklist sections. Run available unit, integration, API, browser, accessibility, performance, security, and architecture checks where the environment supports them. Prefer a local Docker Compose stack and disposable data; use the existing project setup rather than imposing a generic database. Run the optional installed skills when applicable. Save commands, exit codes, outputs, environment, commit, role, URL, and screenshots as evidence. Produce the kit's audit and gap reports.
- `plan`: Merge failures, gaps, architecture findings, and the user's existing plan; check whether planned work already exists. Write the improvement plan and internal decision list using the kit templates. Stop at the plan. Do not generate a client approval checklist or client-facing files unless `$ultimate-qa-client prepare` is invoked.
- `status`: Read `qa-findings/state.json`, current `vN/state.json`, reports, and evidence. Report open, blocked, pending, resolved, and decision items, with a next action. Do not change files.
- `next-version`: Ask for or discover progress sources. Recheck every open, blocked, and pending item against current code and executed checks. Resolve only with evidence; use the original ID for regressions. Run `qa_state.py next-version --project <root>` only after reconciliation. The new state carries unresolved items only. Keep prior versions intact and write `00_Carry_Over.md` plus `VERSIONS.md` from the state and evidence. Then audit for new issues.

## Combined workflow

1. **Initialize or resume.** Read any existing state, requirements, reports, and evidence. Initialize only when state is absent and the output directory is safe to initialize. If initialization was interrupted after state creation, complete missing intake or templates without resetting state or replacing user answers. Ask only unanswered intake questions and continue after the reply. An explicit request to skip intake allows recorded assumptions; silence never grants permission. Stop if the project root, state, or required permissions cannot be established.
2. **Audit.** Default to all relevant checklist sections, honoring the project's recorded scope and limits. Use `set-stage --stage auditing` while working. A file's existence does not prove the stage finished: inspect coverage, evidence, recorded commit, and current working-tree changes before reusing results. Complete draft or stale checks and archive reports before updating them. Missing Docker, credentials, or a device blocks only dependent checks; continue available checks and carry the limitations into the plan. Do not create a test harness or modify application code during QA.
3. **Plan.** Complete the improvement plan from the audit, gaps, existing plans, and ideas. Mark `planned` only when the required reports and evidence references have been checked. Preserve finding IDs and prior versions. If the current review is already complete and still applicable, report its result without opening a new version; use the separate `next-version` command for a new review version.
4. **Optional client preparation.** Only with `--client`, read and apply the installed `ultimate-qa-client` skill's `prepare` workflow after the audit and plan are complete. If the skill, Word dependency, or renderer is missing, keep the completed QA outputs, report the exact missing prerequisite, and leave client preparation pending. Never claim unrendered Word documents were visually verified. Preserve returned client decisions on reruns. Set `awaiting_client` only after the requested client deliverables are ready.
5. **Report.** Give the project root, QA version, report paths, executed checks, and unresolved limits. Without `--client`, create no client files. If paused or blocked, state the remaining step and repeat the original invocation, including `--client` when supplied, so it can resume.

## Evidence rules

Wait for each command or asynchronous job to finish; poll its process/session until an exit result or documented timeout. A started command, pending browser navigation, container health transition, or queued test is not a failure or a manual check. Retry only when a transient cause is evidenced. Classify a completed check as pass, fail, blocked, inconclusive, or genuinely manual; save the reason and exact next step. Never turn an unavailable Docker daemon or missing test account into an application defect. Static source review is useful but cannot prove runtime behavior.

Use `qa_state.py set-stage` to track version progress, `add` for stable finding IDs, `set-status` for evidence-backed transitions, and `reopen` when a closed issue regresses. Previous states are historical snapshots. Do not silently carry resolved or rejected items into the next active backlog. Secrets stay out of logs and reports. Destructive tests require the kit's isolated-environment gate and restore plan.

For Docker setup, read `ultimate-qa-environment` if installed. Use `ultimate-qa-browser`, `ultimate-qa-accessibility`, `ultimate-qa-api`, `ultimate-qa-performance`, `ultimate-qa-architecture`, and `ultimate-qa-security` where they fit the project. Their absence does not prevent the core audit: apply the same evidence rules and record capability gaps. Use `ultimate-qa-client` only when a client-facing workflow is requested. Client decisions do not change QA finding status without evidence.
